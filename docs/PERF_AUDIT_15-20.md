# Performance audit — план.txt §18 («Производительность»)

Scope: read-only audit, без правок. Выполнен, пока другие сессии активно
редактировали `src/pages/Configurator/*` (объединение геометрии, UI
сохранения/экспорта) — исправления оставлены тому, кто возьмётся за них
следующим. Чеклист: план.txt строки ~625-649 (§18).

## 1. Конвейер рендера (src/pages/Configurator/render/)

**Жизненный цикл воркера**
- `render/client.ts:17` — `const workers: (Worker | null)[] = [null, null];` —
  модульный singleton, создаётся один раз за загрузку страницы и никогда не
  `.terminate()`-ится (проверено grep: вызовов `.terminate(` в
  `src/pages/Configurator` нет). Приемлемо для SPA, где конфигуратор —
  единственный потребитель, но пути очистки вообще нет. Если приложение
  станет многостраничным с повторной навигацией, либо dev HMR порождает новые
  инстансы, старый воркер и его `RoomRenderer` (текстуры, изображения юнитов,
  запечённые комнаты) не освобождаются до закрытия вкладки. Исправление:
  экспортировать `disposeWorkers()` из `client.ts` и звать его при
  размонтировании/смене маршрута, либо явно задокументировать как
  singleton на время жизни страницы.

  **Исправлено**: `render/client.ts` экспортирует `disposeWorkers()` —
  `.terminate()` на оба слота, обнуляет ссылки, отклоняет все незавершённые
  запросы вместо того, чтобы оставить их висящими промисами. Вызывается из
  `Configurator.tsx` (`useEffect(() => disposeWorkers, [])`) — то есть при
  размонтировании всей страницы конфигуратора (переход на другой роут), а НЕ
  при переключении между шагами «настройка»/«отделка» внутри неё: `usePlanViews`
  монтируется/размонтируется вместе с `FinishStep`, который размонтируется на
  каждом возврате к шагу 1, так что вызов оттуда просто бы попусту убивал и
  пересоздавал воркеры при обычной навигации по шагам. Подтверждено `tsc
  --noEmit`, `vite build`, `test:geometry` (31/31), `test:server` (22/22).
- `render/client.ts:36-44` (`w.onerror`) — при падении `pending` очищается и
  оба слота воркера обнуляются, но сами мёртвые объекты `Worker` явно не
  `.terminate()`-ятся перед сбросом (рассчитывает на GC после потери ссылки);
  вокруг самого хендлера нет try/catch.

**Рост per-plan кэша**
- `render/renderer.ts:57,83-93` — `RoomRenderer.built` — это
  `Map<string, Built>`, который никогда не очищается/не вытесняется. Каждый
  отдельный ключ (комбинация форма+остекление, см. `usePlanViews.ts:195`
  `${state.vam.shape}|${state.vam.glazing}`) получает постоянную запись с
  полной `RoomModel` и запечёнными картами света (`bakeLight`, один
  `Float32Array` на крупную грань с плотностью текселя 50мм —
  `lighting.ts:28`). На практике ограничено размером каталога (конечное число
  комбинаций форма×остекление), то есть не настоящая неограниченная утечка,
  но не задокументировано и без верхней границы.
- `render/worker.ts:39-40` (`textures`/`units` Map внутри `RoomRenderer`, плюс
  `loading` Map) — тот же паттерн: растёт с каждым отдельным URL
  текстуры/юнита/мебели, запрошенным за сессию, никогда не вытесняется.
  Ограничено размером каталога сегодня; механизма вытеснения нет, если
  каталог отделки сильно вырастет.

**Нет отслеживания «грязных» областей — полная перерисовка на каждый вызов**
- `render/renderer.ts:96-119` (`render()`) — каждый вызов полностью очищает
  целевой буфер (`resetTarget`, строка 100) и перерисовывает КАЖДУЮ видимую
  грань каждого слоя через `drawFace` (строки 106-116), даже если изменился
  только цвет/текстура одной поверхности. Нет списка «грязных» слоёв, нет
  частичной перерисовки, нет инкрементального компоузинга — подтверждено
  `raster.ts:21-31` (`makeTarget`/`resetTarget` делают полный `.fill()`
  буфера) и циклом `for (const layer of LAYERS)`, у которого нет пропуска
  неизменённых слоёв. Единственное реальное кэширование — одноразовая запечка
  геометрии+света на ключ (`renderer.ts:83-93`); шаг шейдинга/компоновки
  (`shade()`, `drawFace()`/`span()` в `raster.ts:192-408`) пересчитывается
  на 100% каждый кадр. Исправление: отслеживать, какие записи
  `paint.surfaces[...]` изменились с прошлого рендера, и перерисовывать
  только грани затронутых слоёв поверх предыдущего кадра вместо
  `resetTarget`+полной перерисовки — прямое соответствие пункту плана
  «повторное использование обработанных ресурсов».
- `render/raster.ts:462-495` (`resolve()`) — полный supersampled буфер
  (`w*h*ss*ss` работы) уменьшается на каждый вызов, согласуется с находкой
  выше про полную перерисовку.

**Transferable-буферы**
- `render/worker.ts:84` — `ctx.postMessage(res, [out.rgba.buffer,
  out.ids.buffer])` корректно передаёт (не копирует) пиксельные буферы
  обратно в главный поток. Уже оптимально, соответствует требованию плана
  «корректно освобождай ресурсы». Правок не требуется.

## 2. Перерисовки React

- `usePlanViews.ts:89` — `const paintKey = useMemo(() => JSON.stringify(paint),
  [paint])` корректно защищён: `paint` мемоизирован выше, в
  `FinishStep.tsx:193` (`const planPaint = useMemo(() => vamRenderPaint(state.vam),
  [state.vam])`), так что `JSON.stringify` пересчитывается только при
  изменении `state.vam`, а не на каждый рендер. Хорошая практика уже
  применена — находки нет.
- `usePlanViews.ts:86-144` — цикл рендера с правилом «последний побеждает»
  (ссылки `running`/`dirty`, строки 93-128) корректно объединяет быстрые
  последовательные изменения (например, перетаскивание слайдера) в один
  выполняющийся рендер плюс максимум один повторный. Уже реализует разумное
  смягчение требования «разумное количество перерисовок» — этот паттерн
  нужно сохранить.
- `FinishStep.tsx:234` — `layers={vamViewLayerUrls(screen, i as 0 | 1,
  state.vam.picks)}` строит НОВЫЙ массив на каждый рендер (не мемоизирован),
  для каждого инстанса `VamScene`, при любом изменении состояния где угодно в
  `FinishStep` (например, переключение несвязанного чекбокса `extras`, который
  живёт в том же общем `ConfigState`, перерисовывает `FinishStep` и
  пересчитывает это для обоих видов, хотя цвета/слои не менялись).
  `VamScene.tsx:46` всё же защищает дорогую часть (`signature =
  layers.join('|')` питает зависимость эффекта на строке 60, так что
  предзагрузка изображений перезапускается только когда список URL
  реально изменился) — так что видимая пользователю стоимость низкая, но
  работа по построению массива/join тратится впустую на каждый несвязанный
  рендер. Исправление: `useMemo(() => vamViewLayerUrls(screen, i,
  state.vam.picks), [screen, state.vam.picks])`.
- `ConfiguratorContext.tsx:16-24` — значение контекста мемоизировано
  (`useMemo(() => ({ state, dispatch }), [state, dispatch])`), но `state` —
  это один общий объект редьюсера, покрывающий и `extras`, и `vam`, так что
  ЛЮБОЕ отправленное действие (например, переключение `insulation`) создаёт
  новую ссылку `state` и перерисовывает каждого потребителя
  `useConfiguratorState()`, включая `FinishStep`, который заново выводит
  `screen`/`planGeom`/`planPaint` и т.д. Они по отдельности мемоизированы на
  более узких срезах (`state.vam`, `state.vam.shape`/`glazing`), так что
  ДОРОГОЙ пересчёт (пересборка сцены) корректно пропускается, когда меняются
  только `extras` — подтверждено, что именно сценарий «выбор цвета меняет и
  extras» на уровне конвейера рендера НЕ встречается. Но поддерево
  компонентов всё равно полностью перерисовывается (нет `React.memo` на
  `FinishStep`/`PlanScene`/`VamScene`). Низкая критичность при текущей
  мемоизации снизу; стоит `React.memo` или разделение `extras` в отдельный
  контекст, если профилирование покажет подвисания на слабых устройствах.

## 3. Загрузка ассетов (render/assets.ts, public/vam/)

Подтверждена ЛЕНИВАЯ, по требованию, загрузка, а не загрузка всего каталога
целиком (~2300 файлов/~25МБ):
- `render/worker.ts:78-80` — на каждый запрос рендера резолвятся только URL
  текстур, реально упомянутых в `paint.surfaces` (`urls`), изображения мебели
  для выбранного в данный момент вида по каждой категории (`furnUrls`) и два
  изображения оконного юнита (`WIN_HOUSE_URL`/`WIN_FRAME_URL`) через
  `ensureTexture`/`ensureUnitImage` (строки 43-67), каждый мемоизирован по URL
  через `loading` Map, так что параллельные запросы на один URL делят один
  fetch.
- `render/assets.ts:11-77` — `loadTexture`/`loadUnitImage`/`loadEnv` грузят по
  одному URL за раз, декодируют через `createImageBitmap` и ДЕЙСТВИТЕЛЬНО
  вызывают `bmp.close()` (строки 20, 75), чтобы своевременно освободить
  декодированный битмап — корректная очистка, соответствует требованию плана
  «очистку ненужных графических объектов».
- `SetupStep.tsx:58,89` — теги `<img>` с миниатюрами используют
  `loading="lazy"`.
- `VamScene.tsx:95` — теги `<img>` слоёв сцены БЕЗ атрибута `loading`. Это
  основная видимая часть экрана (не за пределами экрана), так что ленивая
  загрузка тут мало помогла бы, но стоит отметить как пробел, если слои
  когда-нибудь окажутся за пределами экрана (например, в галерее сохранённых
  проектов).
- В рамках этого аудита (сфокусированного на render/) не найдено настройки
  Cache-Control/подсказок кэша для `/vam/` в продакшене — раздача `public/`
  через Express — это вопрос бэкенда, не проверялся. `vite.config.ts:42`
  задаёт `Cache-Control: no-cache` для DEV-ONLY middleware `/vam/`
  (`servePublicImages()`) — верно для dev; стоит отдельно убедиться, что в
  проде Express ставит реальный долгоживущий заголовок кэша (вне рамок этого
  аудита).

## 4. Мобильные устройства

Нигде в `src/pages/Configurator` не найдено ветвления по
размеру/устройству (grep на `innerWidth`, `matchMedia`, `isMobile`,
`devicePixelRatio`: ноль совпадений). Один и тот же программный растеризатор
работает с одним и тем же фиксированным разрешением/суперсэмплингом
независимо от устройства:
- `render/client.ts:69-70` — `size = req.size ?? 800; ss = req.ss ?? 2;` —
  захардкоженные значения по умолчанию; ни один вызывающий код не передаёт
  меньший размер/ss для узких экранов. Два вида × 800×800px × 2x
  суперсэмплинг (фактически 1600×1600 цель растеризации на вид, см.
  `raster.ts:21` `makeTarget(size*ss, size*ss)`) выполняется безусловно на
  телефонах с той же попиксельной стоимостью, что и на десктопе.
  Исправление: передавать меньший размер/ss на узких экранах (например,
  через проверку `matchMedia`/`innerWidth` в `usePlanViews.ts` или
  `FinishStep.tsx`), чтобы снизить нагрузку растеризации на слабых мобильных
  процессорах/GPU.

  **Исправлено**: `usePlanViews.ts` теперь читает `window.innerWidth` в момент
  каждого рендера (`pickRenderSize()`, без лишнего resize-слушателя — значение
  просто пересчитывается на следующий рендер) и передаёт `size`/`ss` в оба
  вызова `renderView()`: `≤480px → 420px/1.5x`, `≤768px → 560px/1.5x`,
  иначе прежние `800px/2x`. Безопасно для кэша геометрии: `RoomRenderer.built`
  (раздел 1 выше) кэширует только форму+свет по `key` (форма+остекление),
  независимо от разрешения — целевой растровый буфer (`renderer.ts:96`,
  `if (this.target?.w !== size*ss) this.target = makeTarget(...)`) уже
  поддерживал смену размера между вызовами, просто ни один вызывающий код
  не пользовался этим раньше. Подтверждено `tsc --noEmit`, `vite build`,
  `test:geometry` (31/31) и `test:server` (22/22) без изменений в результатах.
- **ПЕРЕСМОТРЕНО — не дефект.** Исходный вывод этого раздела ("нет
  manualChunks/разбиения для exportPdf.ts/exportSvg.ts") был верен по букве
  (`vite.config.ts` действительно не содержит `manualChunks`), но неверен по
  факту: `exportPdf.ts`'s `downloadSpecPdf()` грузит `pdfmake` через
  динамический `await import('pdfmake/build/pdfmake')`/`import('pdfmake/build/vfs_fonts')`
  изнутри функции, не через статический импорт на верхнем уровне модуля — а
  Vite разбивает по месту динамического `import()`, независимо от того, есть
  ли `manualChunks` или нет. Подтверждено `npx vite build`: `pdfmake-*.js`
  (973kB) и `vfs_fonts-*.js` (855kB) — отдельные чанки, НЕ смешанные с
  `Configurator-*.js` (54.85kB) или основным `index-*.js`; загружаются только
  по клику «Скачать спецификацию (PDF)», не при первой загрузке страницы.
  Живой браузерный прогон (другая сессия, см. её `FINAL_REPORT.md`)
  подтвердил сам экспорт работает корректно (валидный PDF 25.6KB, кириллица
  без артефактов, корректная формулировка про отсутствие цены на сайте).
  `exportSvg.ts` не нуждается в разбиении — использует только нативные DOM API
  (`XMLSerializer`/`Blob`), без тяжёлых зависимостей. **Не требует правки.**

## 5. Мёртвая зависимость zustand

Подтверждено свежим grep: `package.json:47` указывает
`"zustand": "^5.0.14"` как зависимость, но поиск по всему `src/` (кроме
`node_modules`) даёт НОЛЬ совпадений — все найденные вхождения внутри
`node_modules/zustand` (файлы деклараций типов). Управление состоянием
целиком реализовано через `useReducer` в `useConfigurator.ts:87-99`,
поднятый через `ConfiguratorContext.tsx`. Не исправлено здесь (правка
`package.json` оставлена владельцу очистки зависимостей) — отмечено как
будущая задача: удалить зависимость либо начать её использовать.
