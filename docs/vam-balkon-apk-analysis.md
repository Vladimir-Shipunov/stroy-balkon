Источник: `D:\VamBalkon_extract\APK` (только чтение, не изменялся). Цель анализа —
понять, какие категории мебели/отделки использовал оригинальный Flutter-конструктор,
и взять их как референс контента для нашего React/THREE.js конфигуратора

## Как устроен оригинал (кратко)

Чистая 2D-компоновка слоями во Flutter (`Stack`), без 3D/WebGL/glTF — в ассетах нет
ни одного 3D-формата.

- `stenaN` (1–10) — преднарисованный **шаблон формы/раскладки балкона** (силуэт с
  вырезом под окно/угол), не материал. Подтверждено строками из `libapp.so`:
  `Kafel_5stena_Gobrazny_balkon`, `MDF_1stena_Gobrazny_balkon` («Gobrazny» = Г-образный
  балкон).
- Материал (`vagonka`, `sten_parket`, `mdf`, сам `stenaN` как база) — текстура,
  **уже вырезанная по силуэту конкретной формы** и запечённая как готовое изображение
  (отсюда сотни файлов — {форма} × {цвет} перебраны заранее, а не тайлятся на лету).
- Мебель/аксессуары (`chair`, `shkaf`, `dryer`, `flowers`, `lamp*`, `plintus*`) —
  PNG/WEBP-спрайты с прозрачным фоном, уже размещённые в нужной позиции на канвасе
  нужного размера (проверено визуально).
- Индекс `_0` почти во всех сериях — служебный **пустой кадр-заглушка** (ровно 66
  байт, полностью прозрачный) = «ничего не выбрано». Реальный контент начинается с
  `_1`. Каталог помечает такие файлы `isEmptyPlaceholder: true`.
- `cvetN` = номер цветового варианта (подтверждено файлами `chair_cvet0…10.webp`,
  `flowers_cvet0…3.webp` в `assets/images/icon/`).
- Числа кадров после `_frame` — вероятно варианты под разные формы/размеры балкона,
  а не углы поворота (косвенно: `lamp1_3.webp` — ряд потолочных споттов разной
  длины). **Не доказано на 100%** для всех категорий — помечено как гипотеза.
- Калькулятор цены в оригинале существовал (`calculator_N_stena.dart`,
  `_calculatePriceVagonka`, `_fetchVagonkaSutepleniemPrice`), но сами числа цен не
  хранятся локально (видимо, тянулись с сервера) — реальных цен из APK не извлечь,
  свои цены зададим сами через админку (см. Step 18/19 общего плана).

\* «Отличных объектов» = после группировки по (категория, базовое имя без номера
кадра) — то есть реальное число разных моделей/цветов, без учёта кадров/пустышек.
Точная граница между «это цвет» и «это кадр под другую форму балкона» не всегда
однозначна по одним именам файлов — где были сомнения, каталог просто группирует
по общему префиксу имени (см. предупреждение выше про кадры).

Дополнительно найдено вне `construktor/` (не в оригинальном брифе, но релевантно):
- `assets/images/icon/*.webp` — иконки категорий с человекочитаемыми русскими
  названиями (URL-decoded из имени файла) — использованы как справочник названий
  выше и как готовые превью-иконки для панели категорий на сайте.
- `assets/images/*.webp` в корне (не construktor) — маркетинговые/декоративные фото
  балконов (`1_4m_l.webp` и т.п.), похоже, экраны выбора формы балкона — НЕ ассеты
  материалов, для каталога не тянулись.
- `assets/animation/*.json` — Lottie-анимации (заставки), не относится к конфигуратору.

## Структурированный каталог (сгенерирован автоматически)

Скрипт: [`scripts/analyzeApkCatalog.mjs`](../scripts/analyzeApkCatalog.mjs) (Node +
`sharp`, только читает `D:\VamBalkon_extract\APK`, ничего там не меняет). Запуск:
`node scripts/analyzeApkCatalog.mjs`.

Вывод:
- [`docs/apk-catalog/catalog-full.json`](apk-catalog/catalog-full.json) — 2240
  записей, по одной на файл: `category`, `parentChain`, `shapeVariant`,
  `sizeVariant`, `name` (база имени без кадра), `colorIndex` (если есть `cvetN`),
  `frame`, `isEmptyPlaceholder`, `file`, `ext`, `fileSizeBytes`, `width`, `height`,
  `aspectRatio`, `avgColorHex`.
- [`docs/apk-catalog/catalog-summary.json`](apk-catalog/catalog-summary.json) —
  свёрнуто по «логическому объекту» (без кадров): те же поля + `frameCount`,
  `emptyFrameCount`, `sampleFile`.

**Ограничение `avgColorHex`:** средний цвет из 1×1 downscale надёжен только для
материалов стен/пола (`stenaN`, `vagonka`, `sten_parket`, `mdf`,
`laminat_podokonnik`) — там картинка почти полностью непрозрачна. Для спрайтов
мебели (`chair`, `shkaf`, `dryer`, `flowers`, лампы) фон прозрачный и сильно тянет
средний цвet к чёрному — эти значения не отражают реальный цвет объекта, для них
нужно смотреть картинку глазами (что и было сделано выборочно, см. отчёт по Step 5/6
в диалоге).

## Что не удалось установить достоверно

- Точная семантика числа кадров >10 у `shkaf`/`vagonka`/`sten_parket` (под форму
  балкона vs. под что-то ещё) — гипотеза, не факт.
- Почему `vagonka`/`sten_parket`/`mdf` покрывают не все 10 `stenaN` (видел 8 из 10 в
  выборке) — либо не все формы поддерживают все материалы, либо часть кадров ушла в
  другую вложенность, которую скрипт не разобрал отдельно.
- Реальные цены материалов в оригинале — не хранятся локально, будем считать что
  оригинальные бесполезны, свои цены задаём сами.
